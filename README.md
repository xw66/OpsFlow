# OpsFlow

### 智能工单与 SLA 管理平台

OpsFlow 面向企业内部客服、IT 运维和售后支持，将问题提交、分配、处理、反馈和归档放在同一条业务流程中。员工能看到问题由谁负责、处理到哪一步；客服按队列接单；组长跟进超时问题和成员工作量；管理员维护服务组织与处理规则。

项目采用 **Java 25 + Spring Boot 4 + Vue 3** 开发。后端围绕权限、工单状态机、并发分配、SLA 时限和可靠消息展开，AI 提供分类、摘要和回复建议，处理决定由业务人员确认。

## 项目解决什么问题

一个问题可能先由客服接收，再交给技术人员排查，中途需要用户补充信息，最后还要确认结果并归档。OpsFlow 用工单记录这段过程，并保留责任人、处理时限和操作记录。

| 业务需要 | 系统中的处理方式 |
| --- | --- |
| 问题有人负责 | 按分类找到客服组，结合在线状态与活动工单量分配负责人 |
| 进度可以追踪 | 集中展示状态、公开回复、内部备注、附件和操作历史 |
| 服务时限可执行 | 创建时确定首次响应与解决截止时间，自动预警并升级超时工单 |
| 跨角色协作有边界 | 用户看自己的工单，客服处理本人负责的工单，组长管理本组，管理员管理全局 |
| 重试不产生重复业务 | 创建请求幂等、数据库版本控制、事务事件表和消息消费去重 |
| 交接时快速了解上下文 | AI 汇总交流内容，提供分类和回复草稿，由人员审核采用 |

## 后端设计

系统以一个 Spring Boot 应用承载业务，按认证、客服组织、工单、SLA、消息、AI 和统计分包。MySQL 保存工单及其变更事实；Redis 用于缓存、幂等控制和限流；Kafka 处理通知、智能分析请求和统计刷新。

```mermaid
flowchart LR
    Web[Vue 3 工作台] --> Auth[Spring Security / JWT / RBAC]
    Auth --> Ticket[工单业务与状态机]
    Ticket --> DB[(MySQL)]
    Ticket --> Redis[(Redis 缓存 / 幂等 / 限流)]
    Ticket --> Outbox[同事务写入 Outbox]
    Outbox --> Publisher[租约领取与重试投递]
    Publisher --> Kafka[Kafka]
    Kafka --> Notify[幂等消费与站内通知]
    Kafka --> Stats[标记日报并重算统计]
    Kafka --> AI[异步分析任务]
    AI --> Model[Spring AI / 结构化校验]
    Model --> Review[人工查看与采纳]
    Review --> Ticket
    SLA[按截止时间分页扫描] --> DB
    SLA --> Outbox
```

### 状态机与并发控制

每次工单更新同时校验当前状态和 `version`，再写入操作历史、审计及业务事件。两个请求竞争同一版本时，数据库只允许一个成功，另一请求返回 `409`，由页面提示刷新。

```mermaid
stateDiagram-v2
    state "已创建" as CREATED
    state "已分配" as ASSIGNED
    state "处理中" as PROCESSING
    state "等待用户回复" as PENDING
    state "已解决" as RESOLVED
    state "已关闭" as CLOSED
    state "已取消" as CANCELLED
    [*] --> CREATED
    CREATED --> ASSIGNED: 分配
    ASSIGNED --> PROCESSING: 接单
    PROCESSING --> PENDING: 挂起
    PENDING --> PROCESSING: 恢复
    PROCESSING --> RESOLVED: 解决
    RESOLVED --> CLOSED: 关闭
    CREATED --> CANCELLED: 取消
    RESOLVED --> PROCESSING: 组长或管理员重新打开
    CLOSED --> PROCESSING: 组长或管理员重新打开
```

自动分配先按分类找到客服组，排除离线、停用及已撤销客服角色的人员，再按活动工单量、最近分配时间和用户 ID 排序。活动工单包含已分配、处理中和等待用户回复三种状态。分配通过组级数据库行锁和工单版本更新协调并发，没有合适人员的工单保留在人工分配队列。

### 本地事务与可靠消息

工单更新与 Outbox 事件写入同一个本地事务。后台使用 `FOR UPDATE SKIP LOCKED` 领取待发送事件的租约，在事务外投递 Kafka，收到确认后标记发送成功；失败事件退避重试，过期租约可重新领取。

消费端以“消费者名称 + eventId”唯一约束去重，消费记录与通知等业务结果同事务提交。异常消息有有限重试、死信队列、失败记录和管理员重放接口。统计按日期标记后重算，重复投递不会重复累加指标。

### SLA、权限与数据保护

| 设计点 | 实现 |
| --- | --- |
| SLA 规则快照 | 创建时保存适用规则及首次响应、解决截止时间，按自然时间计算 |
| 预警与违约 | 按状态和截止时间索引分页扫描，以工单、处理周期和事件类型去重；完成操作同时核对是否超时 |
| 实时权限校验 | 请求中读取账号状态与角色，结合创建者、负责人和客服组检查数据范围 |
| 请求幂等 | Redis 租约减少重复执行，数据库唯一请求键与原始响应快照保障重复提交的一致性 |
| 热点缓存 | 工单详情缓存与事务提交后失效配合，读取时仍校验访问权限 |
| 附件保护 | 校验文件头、文件名、大小和数量；通过授权接口下载，事务回滚时清理新上传文件 |
| AI 调用隔离 | 在工单主事务之外调用模型，设置超时和重试；失败后保留人工处理流程 |

### 数据组织

数据库由 Flyway 管理版本迁移，按业务职责划分：

| 领域 | 主要数据表 |
| --- | --- |
| 用户与组织 | `app_user`、`role`、`user_role`、`support_group`、`support_agent` |
| 工单与交流 | `ticket`、`ticket_category`、`ticket_assignment`、`ticket_comment`、`ticket_status_history`、`ticket_attachment`、`ticket_tag` |
| 服务时限 | `sla_policy`、`sla_event` |
| 智能辅助 | `ticket_ai_analysis`、`ai_call_log` |
| 消息与审计 | `outbox_event`、消费去重记录、通知、消费异常及审计记录 |
| 统计 | 每日统计与刷新任务 |

查询索引围绕用户与创建时间、负责人与状态、状态与截止时间、分类与优先级建立。完整字段和索引见[数据库设计](docs/database-design.md)。
