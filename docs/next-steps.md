## 产品与技术边界

沿用 JDK 25 和现有依赖，不为后续页面主动升级或降级。保持单体后端、MySQL 事务和现有 Outbox；仅补页面真正需要的接口。

界面围绕角色下一步任务组织：用户提交和补充问题；客服处理待办；组长处理升级及分配；管理员维护配置。沿用白色与雾灰背景、青蓝主色、清晰文字和轻分隔线。工单内容与下一步操作优先，AI 默认折叠，不建设聊天入口。

业务状态与 SLA 违约标记分离；按 24×7 计时，PENDING 不暂停。AI 失败不阻塞工单，回复草稿必须人工确认发送。所有权限以服务端资源授权为准。

每行是一个独立开发模块，按顺序实施。每个模块完成相关测试、前端类型检查与构建、更新验收记录后，再进入下一行。跨模块复用现有能力，不提前建立空目录或通用框架。

## 必要接口与数据库变更

- `GET /api/workspace/tickets/{id}/assignment-candidates`：按工单授权返回分页候选，包含身份、组和负载；CREATED 仅提供可用于当前分配的候选。普通客服限同组，跨组需管理员或同时管理源组和目标组的组长；写入时仍重新校验。
- `GET /api/admin/users`：账号/姓名搜索、角色和启用状态筛选，返回安全用户视图及分页信息，禁止返回密码摘要等字段。
- 扩展工作台组、升级与待人工分配筛选；查询条件与权限取交集，不能前端过滤当前页冒充完整队列。
- 为评论、历史和成员列表补必要显示名称，优先联表或批量查询；通知增加本人未读计数。
- 沿用现有数据库结构、索引、统一响应与 version 协议。确认现有结构无法满足需求时才增加 Flyway 迁移；本计划不预先创建新表。

1. 业务测试：保留现有状态机、接单并发、Outbox 一致性、Kafka 幂等、SLA、AI 校验及接口权限测试；修改相关业务时加入能检出错误的针对性检查。

4. 性能与恢复：复用现有 k6 脚本测创建吞吐量、列表 P95、并发接单结果；另记录 SLA 扫描耗时、Kafka 积压及恢复。检查最终数据库副作用，不能仅统计 HTTP 成功数。
5. 每份报告记录提交或工作区状态、设备资源、版本、数据量、并发、持续时间、命令、原始输出和失败项。历史结果与本次结果分开存档；未执行、失败、跳过不得写为通过。
