# 简历与演示材料

## 可直接改写的项目描述

**OpsFlow｜智能工单与SLA管理平台｜个人后端项目**

技术栈：Java25、Spring Boot4.1.1、Spring Security7、MyBatis、MySQL8.4、Redis8、Kafka4.3.1、Spring AI2.0.1、Docker Compose。

- 实现用户、客服、组长及管理员的JWT+RBAC权限控制，覆盖工单创建、交流、分配、转派、挂起、解决、关闭及受限重开；以状态和版本条件更新防止并发覆盖，保留状态历史与操作审计。
- 使用本地事务+Outbox保证工单与事件一致，通过数据库租约、消费去重、有限重试及DLT处理重复投递与故障恢复；SLA采用deadline索引和定时分页扫描，异步生成通知与统计刷新任务。
- 使用Redis实现授权详情缓存、创建幂等租约和接口限流，数据库唯一键保证Redis故障时不重复建单；接入结构化AI分类、摘要和回复草稿，服务端校验并要求人工确认。
- 使用真实MySQL/Kafka/Redis集成测试与k6定位共享标签死锁，通过调整数据库锁顺序修复；同工单32路接单验证仅1次成功，其余31次为预期冲突。当前短测中创建约69.41次/秒、列表P95约26.54ms，均为本机固定窗口结果。

可选实测补充：当前工作区证据为10 VU/30秒创建2091单、约69.41次/秒，列表14365次、P95约26.54ms；必须注明这是开发环境短测，关闭了限流、自动分配及SLA扫描，未调用外部模型；不能写成生产QPS、最高容量或长期SLO。

不要填写生产用户量、真实企业上线经历、模型准确率、节省客服成本、性能提升百分比。初始列表存在2次客户端超时且根因未证实，不能声称所有压测轮次零错误。所有数字需能指向performance.md和results中的对应原始结果。

## 10分钟演示顺序

1. 按README启动依赖和IDEA应用，打开Swagger并登录；展示普通用户无法管理角色，跨用户工单访问被拒绝。
2. 管理员配置客服组、在线客服、分类与SLA；普通用户创建工单，展示deadline、version、初始历史。
3. 客服执行接单、挂起、恢复、解决、关闭，展示审计与版本冲突；使用k6的race模式证明并发只有一个成功。
4. 展示Outbox、站内通知及重复消费幂等；说明broker ACK后崩溃为什么仍可能重复投递。
5. 创建一分钟SLA工单，等待扫描后查看独立违约标记和组长升级记录，不把超时变成非法工单状态。
6. 展示AI建议接口、JSON Schema校验测试、过期建议拒绝及人工确认。没有真实API凭据时明确展示DISABLED结果，不冒充实时推理效果。
7. 查看统计口径与日报刷新时间，最后展示实测报告、死锁诊断、修复和失败轮次。

## 面试可解释的问题

- 为什么使用Outbox后仍不是端到端exactly-once？如何用eventId和数据库事务处理重复？
- 为什么接单只靠synchronized不够？组行锁与工单版本条件分别解决什么竞争？
- 为什么Kafka不当延迟队列？扫描间隔内刚完成的工单如何避免漏记违约？
- 为什么新建空标签关联DELETE会引发间隙锁死锁？修复前后的实际证据是什么？
- Redis故障时哪些功能回源，为什么登录限流选择拒绝？
- 为什么AI只提供建议，采纳时为什么还要检查当前工单版本？
