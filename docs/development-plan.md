## 1. 项目目标与交付方式

面向企业内部客服、IT 运维和售后场景，开发可在 IDEA 中运行、可演示、可测试的 Java 后端项目。核心能力是权限、工单流转、分配、SLA 和消息可靠性；AI 仅提供分类、摘要和回复草稿。

采用单体 Spring Boot 应用、按业务功能分包。每轮只开发一个可运行模块，完成测试、更新文档后再进入下一轮。先提供 Swagger，Vue 3 + TypeScript 在后端闭环后作为独立验收阶段。

**后端阶段 01–11 已按当时范围验收；当前工作区 JDK25 后端回归为180项通过并打包，前端35项测试、生产构建和8项隔离 Chromium 场景通过。历史压测与故障演练保留原始记录；真实外部模型效果和生产容量未验证。**

## 4. 开发阶段

### 阶段 01：工程基础

- 范围：JDK 25 + Boot 4.1.1，统一响应、异常处理、安全默认拒绝、服务信息、Actuator health、Swagger、Compose。
- 明确工单状态转换和受限重开规则，先用纯规则测试固定行为。
- 接口：`GET /api/system/info`、`GET /actuator/health`、`/swagger-ui/index.html`。
- 验收：Maven 测试通过，Swagger 有真实接口定义，匿名受保护请求返回 401，已认证无权限返回 403，错误不泄露内部异常。
- 限制：状态规则测试不代表数据库并发控制已实现；Compose 配置校验不代表容器启动成功。

### 阶段 02：用户认证与 RBAC

- 表：`app_user`、`role`、`user_role`，引入 MyBatis、MySQL 驱动、Flyway。
- 接口：注册、登录、当前用户、管理员启停用户和分配角色。
- 注册只能获得 USER；用户名唯一约束，密码使用 Spring PasswordEncoder；禁止客户端指定管理员角色。
- JWT 使用 Spring Security 原生编码/解码能力，检查签名、有效期和 issuer；密钥从环境注入，不提交仓库。
- 每次授权检查账号是否停用及当前角色，避免旧 JWT 在停用或降权后继续访问。
- 暂只发有期限的 access token；明确退出清理客户端令牌，不冒充服务端主动吊销。
- 无默认公开管理员密码；通过显式初始化流程创建第一个管理员。
- 验收：正常登录、密码错误、重复注册并发、伪造/过期 JWT、停用账号、越权分配角色测试；真实 MySQL 迁移与回滚测试。

### 阶段 03：组织、分类与 SLA 规则配置

- 表：`support_group`、`support_agent`、`ticket_category`、`sla_policy`。
- 接口：管理员管理组织、客服、分类和 SLA；客服设置在线状态；组长查看本组成员。
- 分类对应一个客服组；一位客服第一版属于一个组。在线与账号启用分别校验。
- 分类 + 优先级只能有一条有效 SLA 规则；时限必须为正，首次响应时限不得晚于解决时限。
- 验收：分类路由、规则唯一性、非法时限、禁用记录和角色权限测试。

### 阶段 04：工单 CRUD 与交流

状态：已完成，2026-09-08，113项完整回归通过。附件第一版是本地文件存储，类型头校验并强制下载，不包含恶意文件扫描。Kafka 尚未投递，Outbox 记录保留待阶段 06 处理。

- 表：`ticket`、`ticket_comment`、`ticket_tag`、`ticket_tag_relation`、`ticket_attachment`、`ticket_status_history`、`outbox_event`、`audit_log`。
- 接口：创建、分页查询、详情、受限修改、取消、评论、附件上传和授权下载。
- 工单创建计算明确 deadline，保存 SLA 快照；事务内写工单、初始历史和 `TicketCreatedEvent` Outbox。
- 普通用户只能操作自己的工单；内部备注对用户不可见；修改和取消限制在 CREATED，变更使用 version。
- 附件限制数量、大小和类型，随机存储名、禁止路径穿越，下载必须校验所属工单访问权；第一版使用本地存储。
- 验收：数据归属权限、字段校验、分页上限、非法附件、数据库异常时工单与 Outbox 同时回滚。
- 本阶段只落 Outbox，尚不投递 Kafka；待阶段 06 接通。

### 阶段 05：状态流转与客服分配

状态：已完成，2026-09-09，121项完整回归通过。分配使用组行锁及 READ COMMITTED，工单条件更新兜底；普通 API 冲突返回409，自动扫描失败保留队列并在后续轮次重试。

- 表：`ticket_assignment`，扩展工单历史和审计记录。
- 接口：分配、接单、转派、挂起、恢复、解决、关闭、受限重新打开、待人工分配列表。
- 根据分类找到客服组，排除离线/停用人员，按活动工单数、最后分配时间、用户 ID 排序。
- 活动负载统计 ASSIGNED、PROCESSING、PENDING，避免刚分配但尚未接单的工单不计负载；另提供纯 PROCESSING 指标。
- 无候选人保留 CREATED 且未分配，进入人工列表；不新增无意义的队列表。
- MySQL 带状态与 version 条件更新；影响行数为 0 返回 409，事务内同时保存状态历史、分配记录和 Outbox。
- 分配到不同工单的公平性使用短事务按客服组锁定数据库记录，并在获得锁后查询最新负载；不引入分布式锁。
- 首次有效客服公开回复或处理响应记录 first_response_at；仅自动分配不算首次响应。
- 验收：49 种普通状态组合、受限重开权限、同工单多线程接单仅一个成功、无候选人、跨组越权、版本冲突、失败无孤立历史。

### 阶段 06：Outbox 与 Kafka

状态：已完成，2026-09-09。修复测试代理故障恢复后，完整129项测试通过，0失败、0错误、0跳过，并完成打包。证据为 `target/module-06-test.log`；测试覆盖真实 broker ACK 后未标记 SENT 的租约恢复、重复消费、停机恢复、DLT 和权限重放。第一版使用站内通知，不包含外部短信/邮件及统计业务。

- 表：`consumed_event`、`consumer_failure`、`notification`；完善 `outbox_event` 的重试和租约字段。
- 事件：Created、Assigned、StatusChanged、SlaWarning、SlaBreached、AiAnalysisRequested，携带 eventId、ticketId、ticketVersion、occurredAt、schemaVersion。
- 投递器分页领取待发送记录，数据库租约支持多实例；收到 broker ACK 才标记 SENT，失败退避，进程崩溃后租约可恢复。
- Kafka key 使用 ticketId；不承诺多个 Outbox 投递器天然严格有序，消费者更新投影时检查版本，通知使用事件快照。
- 消费幂等记录和数据库副作用处于同一事务；重复事件不重复新增通知或统计。
- 有限重试后进入 DLT，记录异常；DLT 投递失败不能提交原消息 offset；提供可审计的人工重放入口。
- 第一版通知采用站内通知，外部邮件/短信以后按业务需要接入。
- 验收：重复消费、发送后更新 SENT 前崩溃、消费者副作用失败、Kafka 停机恢复、DLT 重放、租约过期恢复。

### 阶段 07：SLA 扫描与升级

状态：已完成，2026-09-09，完整137项测试通过，0失败、0错误、0跳过，打包成功。扫描使用已有状态/deadline索引及有界游标；完成操作同步补记扫描间隔内发生的违约。第一版仅升级到组长（级别1），保留累计标记与重开历史；不实现工作日历、暂停计时及多级升级规则引擎。

- 表：`sla_event`，补全扫描索引。
- 第一版按 24×7 自然时间计算，PENDING 不暂停 SLA。暂停计时与工作日历不在第一版范围内。
- 完成时间等于 deadline 算达标，超过才违约。客服公开回复/解决在同一事务内补记已经发生的违约，避免完成后从扫描候选中移除而漏记。
- 响应和解决分别扫描；截止时间索引 + 游标分页 + 单批上限；可配置扫描间隔、提前预警窗口。
- SLA 超时只更新独立的违约标记及升级级别，不引入 BREACHED 业务状态。
- `auto_escalate=false` 仍记录违约及事件，仅不提升级别或触发组长升级处理。
- 用状态/version 条件更新与唯一约束避免重复预警/升级，事务内写 SLA 事件和 Outbox。
- 重开保留历史违约，增加 sla_cycle，重算解决 deadline；首次响应时间保留，不重新统计。
- 验收：固定 Clock 的临界时间、响应完成后不再响应违约、已关闭跳过、多页扫描、多实例重复扫描、解决与扫描并发。

### 阶段 08：Redis 缓存、幂等与限流

状态：已完成，2026-09-09，完整145项测试通过，0失败、0错误、0跳过，打包成功。创建API必填Idempotency-Key；MySQL持久保存请求摘要与首次响应，Redis仅承担15秒租约。详情缓存30秒并在提交后失效；限流按固定60秒窗口执行，登录保护在Redis故障时拒绝请求。测试证据为 `target/module-08-test.log`。

- 热点详情使用 cache-aside 与有限 TTL；缓存命中也检查数据权限；事务提交后失效缓存。
- 第一版接受有界短暂陈旧读取，状态写入始终以 MySQL 的状态/version 为准，冲突后客户端刷新。
- 幂等键绑定用户、操作和请求体摘要；使用原子 Redis 操作及租约，不能无条件删除他人的锁。
- 创建工单同时用数据库唯一请求键兜底，处理 Redis 成功占位但数据库失败、进程崩溃及键过期场景。
- 限流对用户/IP + 路由组合执行原子计数，返回 429 与 Retry-After。
- 缓存不可用回源；创建靠数据库去重；登录等安全敏感限流不可用时拒绝请求，不能默默放行。
- 验收：缓存越权、更新失效、重复提交同结果、相同键不同请求体冲突、限流并发、Redis 故障降级。

### 阶段 09：Spring AI 辅助

状态：已完成，2026-09-10。完整160项测试通过，0失败、0错误、0跳过，打包成功。已接入分析任务/调用日志、独立Kafka消费组、90秒工作租约和人工采纳。分类修改限CREATED且版本一致；摘要和草稿仅客服侧可见。模型默认关闭；外部真实调用及准确率未验证，不把固定HTTP响应或模拟模型结果当作实际推理效果。

- 表：`ticket_ai_analysis`、`ai_call_log`。
- 创建工单使用人工分类或系统“待分类”分类，异步分析不阻塞主事务。
- 分类输出：category、priority、tags、confidence、reason；摘要和回复建议也映射到明确 DTO。
- 校验有效分类 ID、优先级枚举、标签数量和长度、confidence 范围、文本长度；不信任模型生成的 JSON。
- 三种调用设置有限超时、重试和输入上限；记录模型、实际 token 用量、耗时、结果/失败类型；供应商未返回 token 时记录未知，不填 0 冒充实测。
- AI 建议必须人工采纳；采纳时重新校验工单状态/version，AI 不自动转派、关闭或发送回复。
- 回复草稿与正式评论分开，只有客服确认接口可以发出。
- 验收：非法枚举、越界置信度、超长字段、空输出、超时、模型失败仍创建成功、未确认草稿不可见、建议过期冲突。
- 外部模型测试需真实 API 凭据；离线契约测试与真实调用测试分开记录。

### 阶段 10：统计看板 API

状态：已完成，2026-09-10。修复两个单参数Mapper的actor绑定后，7项真实MySQL专项测试通过；完整167项测试通过，0失败、0错误、0跳过，打包成功。日报按事实表重算，概览明确创建日期样本与当前工作量的区别。未测性能容量。

- 使用 MySQL 聚合查询；需要减少重复计算时才增加日统计表，不引入分析型数据库。
- 指标：每日新增、分类数量、客服处理中数、首次响应均值、解决均值、SLA 达成率、超时数、AI 分类采纳率。
- 默认业务日以 Asia/Shanghai 划分，查询参数转换为 UTC 边界；支持时间范围上限。
- 组长看本组，管理员看全局；所有指标定义样本范围和分母，空样本返回 null/无数据。
- 消费者只幂等触发统计刷新或维护明确的聚合，不能直接重复累加；第一版允许定时从事实表重算。
